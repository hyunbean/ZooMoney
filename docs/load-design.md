# 부하/동시성 설계 문서 (Load & Concurrency Design) — 주머니 (ZooMoney) Dify 게이트웨이

> 이 문서는 **페이퍼 설계**입니다. 실제 구현·부하테스트를 수반하지 않으며, 현재 코드(`gateway/src/index.js`, `gateway/wrangler.toml`, 2026-07-28 기준)를 읽고 확인한 사실에서 출발해 "실제 서비스로 운영하려면 무엇이 필요한가"를 추론합니다.

## 1. 현재 상태 — 코드에서 확인한 사실

`gateway/src/index.js`를 직접 읽고 확인한 현재 구조:

- **하드코딩된 일일 한도:** `const DAILY_LIMIT = 40;` (31행) — **IP당 하루 40회**. Cloudflare Workers KV(`RATE_KV`)에 `rl:{YYYY-MM-DD}:{ip}` 키로 카운터를 저장하고, 25시간 TTL로 자정 이후 자연 소멸시킵니다(`checkRateLimit()`, 50-60행).
- **KV 미바인딩 시 무제한 통과:** `if (!env.RATE_KV) return { ok: true, used: 0 };` (52행) — 로컬 `wrangler dev`처럼 KV가 없는 환경에서는 레이트리밋이 완전히 비활성화됩니다. 이는 개발 편의를 위한 설계이지만, **배포 설정 실수로 KV 바인딩이 빠지면 프로덕션에서도 조용히 무제한 상태가 될 수 있는 잠재 위험**이기도 합니다.
- **큐 없음, 백프레셔 없음:** 요청이 들어오면 즉시 `fetch(DIFY_BASE/chat-messages, ...)`를 호출합니다(101-116행). 대기열, 동시 요청 수 제한, 서킷 브레이커가 전혀 없습니다. Dify 응답이 늦으면 `AbortSignal.timeout(30000)`(115행)으로 30초 후 실패 처리만 합니다.
- **동시성 제어 없음:** Cloudflare Worker는 요청마다 독립 실행되므로, 레이트리밋 카운터 증가(`RATE_KV.get` → `RATE_KV.put`, 55-58행)가 **원자적이지 않습니다.** 같은 IP에서 거의 동시에 여러 요청이 들어오면 두 요청이 같은 `used` 값을 읽고 각자 +1 해서 쓰는 경쟁 조건(race condition)이 이론상 가능합니다 — 다만 하루 40회 규모의 개인용 한도에서는 실질적 피해가 크지 않습니다.
- **비용/관측성:** 요청마다 `agent`, `latency_ms`, `usage.total_tokens`, `usage.total_price`를 구조화 로그로 남기지만(122-131행), 이는 `wrangler tail`로 실시간으로만 볼 수 있고 **영속 저장·집계·알림(alerting)은 없습니다.**
- **에이전트 5개, 시크릿 5개:** `AGENT_SECRETS`에 `goal/analysis/budget/trainer/summary` 5개 키가 등록되어 있습니다(ETF 코치 제거 이후 6번째 시크릿은 삭제됨, `SYSTEM_CARD.md` 참고).

**요약:** 현재 게이트웨이는 "개인 포트폴리오 데모를 남용으로부터 지키는" 수준의 설계입니다. IP당 하루 40회라는 숫자 자체가 이를 보여줍니다 — 실사용자 트래픽을 상정한 용량 계획이 아니라, 데모 링크가 알려졌을 때 청구서가 터지지 않게 하는 안전장치입니다.

## 2. "실제 서비스"로 간다면 — 트래픽 가정

캡스톤 데모를 넘어 실사용자를 받는 서비스가 된다고 가정할 때, 다음은 이 문서를 위한 **가정**이며 실측 데이터가 아닙니다(현재 앱에는 실사용자 트래픽 로그가 없으므로 실측이 불가능합니다):

- 활성 사용자(DAU) 1,000명 가정, 1인당 하루 평균 AI 호출 8~15회(온보딩 2~3회 + 트레이너 챗봇 대화 5~10턴 + 예산 제안 1회 + 소비요약 1~2회) → **하루 8,000~15,000회** 수준. 현재 40회/IP 한도로는 개인당 몇 번만 써도 즉시 429가 뜨는 규모입니다.
- 트래픽은 균등하지 않고 저녁 시간대(퇴근 후 가계부 정리, 21~24시)에 몰릴 가능성이 높습니다 — 순간 동시 요청(concurrency)이 평균보다 훨씬 큰 스파이크로 나타날 것으로 예상됩니다.
- 트레이너 챗봇은 다턴 대화이므로 한 세션이 여러 번의 순차 호출을 만듭니다 — "요청 수"와 "활성 세션 수"를 분리해서 봐야 합니다.

## 3. 현재 하드코딩된 40회/일 한도를 무엇으로 대체할 것인가

| 축 | 현재 | 제안되는 구조 |
|---|---|---|
| 한도 단위 | IP당 고정 40/일 | **사용자 계정 단위**(현재는 계정 개념 자체가 없음 — `SYSTEM_CARD.md` 참고, localStorage뿐이라 IP가 유일한 식별자) + IP 단위를 보조 방어선으로 병행 |
| 한도 구조 | 단일 상수 | **에이전트별 차등 한도** — 트레이너 챗봇(대화형, 저비용 저지연 요구)과 소비분석/예산플래닝(토큰 소모가 큰 구조화 응답)을 분리해 각각 다른 한도·다른 모델 티어를 적용 |
| 시간 창 | 자정 리셋(25h TTL) | 자정 리셋은 "23:59에 다 쓰고 00:01에 다시 다 쓰는" 버스트를 허용함 — **슬라이딩 윈도우 또는 토큰 버킷**으로 전환 필요 |
| 초과 시 동작 | 429만 반환 | 429 + `Retry-After` 헤더 + 남은 한도 안내(사용자가 언제 다시 쓸 수 있는지 UI에 표시) |

**계정 개념이 없다는 근본 문제:** 현재 앱은 서버 측 사용자 계정이 없고(`js/state.js`가 전부 localStorage), 게이트웨이는 IP만 식별자로 씁니다. 실제 서비스라면 인증(최소한 익명 디바이스 ID + 서버 발급 토큰)이 선행되어야 계정 단위 쿼터가 의미를 가집니다. IP 기반 한도만으로는 NAT 뒤의 여러 사용자(회사/학교 네트워크, 캠퍼스 와이파이)가 한도를 공유하게 되는 문제가 이미 지금도 존재합니다.

## 4. 큐가 필요한가

**현재는 없고, 있어야 합니다.** 이유:

- Dify `/chat-messages`는 `response_mode: 'blocking'`으로 호출됩니다(`gateway/src/index.js:111`) — 즉 Worker가 Dify 응답을 받을 때까지 요청을 붙들고 있습니다. Dify(그리고 그 뒤의 GPT-4o-mini/Tavily/Cohere) 쪽 지연이 늘어나면 Worker 요청도 같이 길어지고, 이는 Cloudflare Workers의 CPU 시간/요청 시간 제한에 부딪힐 수 있습니다.
- 순간 동시 요청이 많아지면(3절의 저녁 시간대 스파이크), Dify 계정의 동시 연결 수·분당 요청 수 제한(Dify 측 rate limit, 정확한 수치는 Dify 요금제 문서에서 별도 확인 필요 — 이 저장소 코드에는 명시돼 있지 않음)에 먼저 부딪힐 가능성이 큽니다.
- **제안:** 사용자 요청은 즉시 "접수됨" 응답을 주고, 실제 Dify 호출은 Cloudflare Queues(또는 Durable Object 기반 큐)에서 순차/제한된 동시성으로 처리한 뒤 결과를 폴링 또는 WebSocket/SSE로 전달하는 비동기 패턴으로 전환. 이는 트레이너 챗봇처럼 사용자가 응답을 기다리는 대화형 UX와는 트레이드오프가 있으므로, **대화형 에이전트(trainer)는 현재처럼 blocking 유지 + 동시성 상한(예: 전역 동시 20건)** 을, **비대화형 배치성 호출(소비분석 전체 3개월 분류, 소비요약 월간 리포트)은 큐 기반 비동기**로 분리하는 것이 현실적입니다.

## 5. 레이트리밋 전략

- **다층 방어:** (1) Cloudflare 엣지 레벨의 WAF/Rate Limiting Rules로 초당 요청 수 상한을 걸어 스크래핑성 트래픽을 먼저 걸러내고, (2) 그 뒤에 현재처럼 KV(또는 Durable Object) 기반 사용자별 쿼터를 적용하는 2단 구조.
- **원자성 개선:** 현재 KV `get` 후 `put`은 경쟁 조건이 가능합니다(1절). Durable Object 하나당 사용자(또는 IP)를 매핑해 카운터를 그 안에서 원자적으로 증감시키는 방식이 KV보다 정확합니다 — 다만 사용자 수가 많아지면 Durable Object 수도 늘어나므로 비용/복잡도 트레이드오프가 있습니다.
- **비용 연동 한도:** 현재 한도(40/일)는 "횟수"만 셉니다. 그러나 실제 비용은 에이전트마다, 대화 길이마다 다릅니다(로그에 `usage.total_price`가 이미 찍히고 있음, `gateway/src/index.js:128`). 횟수 기반 한도를 **토큰/비용 기반 한도**로 전환하면 "짧은 질문 40번"과 "긴 소비분석 대화 40번"의 실제 비용 차이를 반영할 수 있습니다.

## 6. 부하가 커지면 가장 먼저 무엇이 깨지는가 — 구체적 병목 순서

코드에서 확인한 현재 구조를 기준으로, 트래픽이 늘어날 때 깨지는 순서를 추론하면:

1. **Dify API 자체의 레이트리밋/동시성 한도가 가장 먼저 걸립니다.** 게이트웨이는 IP당 40/일로 스스로를 제한하고 있지만, 이는 어디까지나 Cloudflare 쪽의 자체 방어선일 뿐 Dify 쪽 한도와 무관하게 설정된 상수입니다. 사용자 수가 늘어 게이트웨이 한도를 여러 사용자가 동시에 채우기 시작하면, Worker가 Dify로 보내는 초당/분당 요청 수가 Dify 요금제의 실제 한도를 넘어설 수 있고, 이 경우 Dify가 429/5xx를 반환하기 시작합니다. 현재 코드는 이 케이스를 "upstream timeout/failure"로만 뭉뚱그려 처리합니다(`gateway/src/index.js:117-120`) — Dify 자체 레이트리밋과 진짜 장애를 구분하지 못합니다.
2. **비용 런어웨이(cost runaway).** `DAILY_LIMIT`을 사용자별로 올리거나 사용자 수가 늘면, 토큰 사용량 로그는 남지만(`usage.total_price`) 이를 실시간으로 합산해 예산 상한을 걸어주는 로직이 없습니다. 만약 한도 로직에 버그가 있거나(예: KV 미바인딩 배포, 1절 참고) 우회가 발생하면 비용이 관측만 되고 차단되지는 않는 상태로 흐를 수 있습니다.
3. **Blocking 호출로 인한 Worker 자원 소모.** 큐가 없는 상태(4절)에서 동시 세션이 늘면, 각 요청이 Dify 응답을 기다리는 동안 Worker 인스턴스가 점유됩니다. Cloudflare Workers는 요청당 격리되어 스케일 자체는 되지만, Dify/OpenAI 쪽 지연이 늘어나는 시간대에는 전체 응답 지연이 사용자 체감상 동시에 나빠집니다(같은 상류 병목을 모든 사용자가 공유하기 때문).
4. **CORS 허용 오리진 목록의 확장성.** `ALLOWED_ORIGINS`가 배열 3개로 하드코딩되어 있습니다(25-29행) — 다중 배포 환경(스테이징, 다국어 서브도메인 등)이 생기면 코드 수정·재배포가 필요한 구조입니다. 트래픽 문제는 아니지만 운영 확장성의 병목입니다.

## 7. 이 문서가 다루지 않은 것

- Dify 자체의 정확한 요금제별 rate limit 수치 — 이 저장소 코드/설정에 값이 없어 확인 불가, Dify 공식 문서/계약 조건에서 별도 확인 필요.
- 실제 부하테스트 수치(RPS, p95 지연 등) — 수행하지 않았습니다. 3절의 트래픽 가정은 설계 논의를 위한 가정치이며 실측이 아닙니다.
- 큐/Durable Object 도입의 구체적 구현 코드 — 이 문서는 설계 방향만 제시하며 구현하지 않았습니다.
