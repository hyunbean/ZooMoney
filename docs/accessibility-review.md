# 접근성 검토 (Accessibility Review) — 주머니 (ZooMoney)

> **중요한 전제:** 이 문서는 **정적 코드 리딩(static code review)** 만으로 작성했습니다. 실제 브라우저, 스크린리더(NVDA/VoiceOver 등), 실사용자 키보드 조작 테스트는 **수행하지 않았습니다.** 아래 findings는 "코드상 존재/부재가 확인되는 것"을 근거로 하며, 실제 렌더링 시 브라우저 기본 동작(예: 포커스 스타일, 네이티브 `<button>`의 키보드 활성화)까지 감안한 실사용성 평가가 아닙니다. 정식 접근성 인증을 대체하지 않습니다.

검토 범위: `index.html`, `css/variables.css`, `css/screens.css`, `css/components.css`, `css/modal.css`, `js/*.js`, `js/screens/*.js` (2026-07-28, `main` HEAD `5f84da3` 기준).

## 1. 색상 대비 (Color Contrast)

`css/variables.css`에 정의된 팔레트를 기준으로 WCAG 2.1 AA 기준(본문 텍스트 4.5:1, 큰 텍스트/18pt 이상 또는 14pt 굵게 이상은 3:1, UI 컴포넌트 경계는 3:1)에 대해 상대 휘도 공식으로 직접 계산한 결과입니다.

| 조합 | 실제 대비율 | AA 본문(4.5:1) | AA 큰 텍스트/UI(3:1) |
|---|---|---|---|
| `--ink`(#3d2817) on `--bg`(#efe2bf) | **10.76:1** | 통과 | 통과 |
| `--ink` on `--surface`(#fbf3d4) | **12.46:1** | 통과 | 통과 |
| `--muted`(#8a6b3f) on `--bg` | **3.83:1** | **실패** | 통과 |
| `--muted` on `--surface` | **4.43:1** | **실패 (근소)** | 통과 |
| `--muted` on `--surface-2`(#e7d4a3) | **3.37:1** | **실패** | 통과 |
| `--accent`(#c2691f) on `--bg` | **3.06:1** | **실패** | 통과(근소) |
| `--white`(#fbf3d4) on `--accent` | **3.54:1** | **실패** | 통과 |
| `--green`(#6b8e3a) on `--bg` | **2.93:1** | **실패** | **실패(근소, 3:1 미달)** |
| `--red`(#b04632) on `--bg` | **4.33:1** | **실패 (근소)** | 통과 |
| `--accent-2`(#d4a05b) on `--bg` | **1.82:1** | **실패** | **실패** |

**코드상 실제 사용처 확인:** `--muted`는 장식용이 아니라 본문 라벨 텍스트로 광범위하게 쓰입니다. 예:
- `css/screens.css:34-35` `.ob-ai-header { font-size: 11px; color: var(--accent); }` — 11px(약 8pt)인데 `--accent`/`bg` 대비 3.06:1. 11px는 "큰 텍스트" 기준(18pt/24px 이상, 또는 14pt/18.7px 이상 굵게)에 전혀 해당하지 않으므로 **AA 본문 기준(4.5:1)이 적용되어야 하는 실패 사례**입니다.
- `css/screens.css:66-67, 209-211, 240-241, 362-364, 386-388, 404-406, 424-426, 519-521, 594-597, 659-661, 838-840` 등 다수의 `.ob-*-label` 클래스가 `font-size: 10~12px` + `color: var(--muted)`. 전부 위와 같은 이유로 소형 텍스트에 4.43:1 이하 대비를 사용 중이라 AA 미달입니다.
- `css/screens.css:664-666` `.ob-budget-box-amount { font-size: 32px; color: var(--accent); }` — 이 경우는 32px(24px 이상)로 "큰 텍스트" 기준에 해당하므로 3.06:1이 근소하게 통과선에 걸쳐 있습니다(3:1 기준 상 통과, 다만 여유가 거의 없음).
- `--accent-2`(1.82:1)는 팔레트에 정의는 되어 있으나 본문 텍스트 색상으로 쓰인 사례는 검토 범위에서 확인되지 않았습니다(장식/하이라이트 용도로 추정) — 다만 향후 텍스트 색상으로 재사용될 경우 가장 위험한 조합입니다.

**결론:** 주조색(`--ink` on `--bg`/`--surface`)은 대비가 매우 우수합니다. 문제는 **보조 텍스트 색상(`--muted`, `--accent`, `--green`, `--red`)을 라벨류의 작은 폰트(10~12px)에 그대로 쓰는 패턴이 화면 전반에 반복**된다는 점입니다. 이 앱은 픽셀 폰트(`DungGeunMo`)를 작은 크기로 많이 쓰는 디자인이라, 대비가 낮은 보조색과 결합하면 저시력 사용자에게 실질적인 가독성 문제가 될 수 있습니다.

## 2. 스크린리더 지원

정적 검색 결과 (전체 `js/` 트리 기준):

- **`aria-*` 속성: 0건.** `role="..."` 속성: 0건. `tabindex`: 0건. 코드베이스 전체에 하나도 없습니다.
- **`alt` 속성은 존재하며 대체로 의미 있는 값을 사용합니다.** 예: `js/screens/home.js:152` `<img src="images/trainer_chat.png" alt="트레이너"/>`, `js/screens/mypage.js:204,233,276,306,329`의 배지 이미지들은 `alt="${badgeDef.name}"`(배지 이름)로 동적 바인딩되어 있어 이미지별로 구별되는 텍스트를 제공합니다. `index.html:30,37`의 스플래시/로딩 이미지도 `alt="주머니"`, `alt="캐릭터"`로 값이 채워져 있습니다. → **이 부분은 통과.**
- **의미론적 랜드마크/헤딩이 화면 대부분에 없습니다.** `<h1>~<h6>`가 코드베이스 전체에서 등장하는 곳은 `js/screens/onboarding.js`뿐입니다(274, 864, 1220, 1270, 1340, 1410, 1478, 1513, 1581행 — 온보딩 5단계 화면 제목). 홈/저금통/마이페이지/커뮤니티/트레이너챗봇/예산/상점 화면은 제목을 전부 `<div class="...">텍스트</div>` 형태로 렌더링하며 헤딩 태그를 쓰지 않습니다. `<nav>`, `<main>`, `<header>` 등 랜드마크 요소도 검색되지 않았습니다(하단 네비게이션도 `renderBottomNav()`가 만드는 `<div>` 구조로 추정).
- **영향:** 스크린리더 사용자는 "제목으로 건너뛰기(heading navigation)"나 "랜드마크로 건너뛰기" 같은 표준 탐색 방법을 온보딩 화면 외에는 쓸 수 없고, 전체 DOM을 선형으로 읽거나 클래스명에 의존해야 합니다. 배지 이미지처럼 `alt`가 잘 채워진 부분은 개별 정보 전달은 되지만, 화면 구조 자체를 파악하기는 어렵습니다.

## 3. 키보드 내비게이션

- **네이티브 `<button>` 요소는 실제로 쓰이고 있습니다.** 예: `js/screens/home.js:71-72` (`#home-hdr-demo`, `#home-hdr-gear`), 147행의 정산 버튼, 192-193/370-371/437-438행 등 모달 확인/취소 버튼. `<button>`은 브라우저 기본 동작으로 Tab 이동과 Enter/Space 활성화를 지원하므로, 이 요소들 자체는 (다른 이슈가 없다면) 키보드로 조작 가능할 가능성이 높습니다.
- **그러나 클릭 가능한 비-버튼 요소들이 다수 존재하고, 이들에는 키보드 대응이 없습니다.**
  - `js/screens/home.js:268-282` — 지출 내역 선택 UI. `el('div', { class: 'expense-item ...' })`로 만든 `<div>`에 `item.addEventListener('click', ...)`만 연결되어 있고, `role="button"`, `tabindex`, `keydown`(Enter/Space) 처리가 전혀 없습니다. 마우스/터치로만 선택 가능합니다.
  - `js/screens/home.js:309` — `streakRow.querySelector('#home-gauge-area').addEventListener('click', _openDrawer)`. 게이지 영역도 클릭으로만 지출 드로어를 여는 `<div>`로, 키보드로 열 수 있는 경로가 없습니다(같은 화면의 다른 방법으로 대체 가능한지는 확인되지 않음).
  - `js/screens/home.js:301-302` — 드로어 오버레이 클릭으로 닫기(`expOverlay.addEventListener('click', _closeDrawer)`)는 있지만, **Escape 키로 닫는 처리(`keydown`에서 `Escape` 감지)는 코드베이스 전체에서 0건**입니다.
- **모달 포커스 관리:** `js/modals.js`에서 `input.focus()` 호출은 2건 확인됩니다(368, 399행 — 닉네임/이름 입력 모달이 열릴 때 입력창에 포커스 이동). 이는 좋은 패턴입니다. 다만:
  - 이 두 모달을 제외한 나머지 모달(확인 모달, 지출 드로어 등)은 열릴 때 포커스를 이동시키는 코드가 없습니다 — 기본적으로 포커스가 이전 위치(예: 방금 클릭한 버튼)에 남아, 스크린리더/키보드 사용자에게는 모달이 열렸다는 신호 자체가 없을 수 있습니다.
  - **포커스 트랩이 전혀 구현되어 있지 않습니다.** 모달이 열린 상태에서 Tab을 계속 누르면 포커스가 모달 뒤 배경 콘텐츠로 빠져나갈 수 있습니다(코드상 트랩 로직 부재를 확인한 것이며, 브라우저의 실제 tab order는 렌더링 테스트로만 최종 확인 가능).
  - Enter 키 처리는 존재하지만 입력창 제출 용도로 한정됩니다: `js/modals.js:369,400`, `js/screens/trainer_chat.js:197`, `js/screens/onboarding.js:308`, `js/screens/social.js:607` — 전부 `e.key === 'Enter'`일 때 전송 버튼을 클릭하는 패턴이고, 일반적인 키보드 내비게이션(화살표 키로 목록 이동 등)은 어디에도 없습니다.

**결론:** 표준 `<button>`을 쓴 부분은 최소한의 키보드 조작 기반을 갖췄지만, 클릭 전용 `<div>` 패턴(지출 항목 선택, 게이지 영역)과 Escape로 닫기/포커스 트랩의 부재는 키보드만 사용하는 사용자에게 실질적인 조작 불가 지점을 만듭니다.

## 5. 이 문서의 한계 (재강조)

- 브라우저에서 실제로 렌더링해 Tab 순서, 포커스 링(outline) 표시 여부, 스크린리더가 실제로 무엇을 읽는지는 검증하지 않았습니다.
- CSS의 `:focus`/`:focus-visible` 스타일 존재 여부는 이번 검토에서 별도로 전수 조사하지 않았습니다 — 버튼에 포커스가 가더라도 시각적으로 보이는지는 추가 확인이 필요합니다.
- 대비율 계산은 `css/variables.css`에 정의된 토큰 값 기준이며, 인라인 스타일이나 이미지 위에 얹힌 텍스트 등 CSS 변수 밖에서 지정된 색상은 전수 검토하지 않았습니다.
